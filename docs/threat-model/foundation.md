# Foundation threat model

Assets: person/employment work-directory data, organization masters, permanent code allocations, active sessions, approved identity bindings and their attestations, branding configuration, business audit and outbox events. Current deployment uses synthetic data only.

Trust boundaries: browser -> API; external IdP -> callback; API runtime -> PostgreSQL; migration operator -> database ownership; worker -> outbox receipt; developer -> public repository.

F0.3 adds a separate identity-operator login -> fixed binding function boundary. Its NOLOGIN writer can read eligibility records and insert an Employee-only binding/attestation/audit; the login itself cannot read those tables or create employment. Human approval references are external attestations, not automatic provider verification. Keep that credential out of API/worker environments. See [ADR 0003](../adr/0003-people-organization-identity.md) and the [operations runbook](../runbooks/identity-operations.md).

Production gaps include portal CSP/TLS gateway certification, distributed rate limits, trusted-proxy validation, independent immutable audit storage, secrets/KMS, encrypted storage/backups, admin provisioning, session cleanup, penetration testing, load testing, manual accessibility and the applicable privacy sign-offs. No claim of ASVS or WCAG conformance is made by passing automated tests alone.

Checklist tasks inherit case scope under FORCE RLS. Candidates can read/update only candidate-owned tasks; internal owner labels grant no employee permissions. Candidate dependency lookup reveals only a waiting flag for their own task. A case lock serializes task changes with review, form saves and credential rotation. Immutable task metadata and same-case prerequisite FKs prevent dependency rewriting/cycles; database triggers enforce completion/reopening order. Candidate checklist mode can increment only the case version, including after submission, and cannot edit approved form data. Required tasks cannot be waived or deleted through runtime grants. Case/task versions and mandatory audit/outbox writes prevent stale or unaudited changes. HR coordination notes remain synthetic, not verified identity/check evidence.

Scoped employee transactions also bind the immutable identity-binding UUID as transaction-local `app.actor_id`. Maker-checker database guards must compare this trusted context, never an actor identifier supplied in a request body. The value clears on commit/rollback and does not turn a role switch by the same identity into an independent reviewer.

Candidate preview adds a separate hostname, listener and restricted database login. Employee and candidate cookies are host-only and never interchangeable. Fragment invitations are removed immediately from the URL; GET does not consume them. Tokens are hashed, OTP hashes are keyed and bound to a challenge, and successful exchange consumes the invitation once. Exact Origin, CSRF, expiry, attempt/cooldown limits and invitation-generation checks protect candidate writes. Session resolution and HR rotation lock the case before credential rows, preventing revoked in-flight writes and conflicting lock order. Immutable submissions and their audit/outbox records commit together. Encrypted delivery previews are a local testing mechanism and do not establish ownership of a real email address. Production startup is blocked for this capability. Authentication telemetry, shared rate limiting, cleanup and independent security review remain gates.
